# Telegram Bot Relay Design

## Goal

Keep Supabase as the PostgreSQL/Auth/RLS/Realtime/Storage platform and add a secure Telegram Bot API integration for account linking, invitations, and notifications. Email/password remains the only application login method.

## Explicit Boundaries

### In scope

- One-time Telegram deep-link invitations generated by an authenticated Centras Chat user.
- Server-side webhook handling for `/start <token>` and private text messages.
- Linking one Telegram identity to one Centras profile.
- Outbound notifications for eligible direct messages.
- PostgreSQL-backed outbox with retries, leases, and idempotency.
- Relay activity visible to the linked user.
- Mock-mode behavior and unit tests without real credentials.

### Out of scope

- Telegram as an authentication provider.
- Reading a user's existing Telegram chats.
- MTProto, Mautrix, phone login, or Telegram user sessions.
- Telegram group synchronization.
- Media/file relay in the first pass.
- Redis, BullMQ, or a separate message broker.
- Replacing Supabase with a raw PostgreSQL driver.

## Architecture

```text
Centras UI
  -> TelegramService / ChatService
    -> authenticated Supabase client (user-scoped reads and link-token creation)

Telegram Bot API
  -> POST /api/telegram/webhook
    -> service-role Telegram repository
      -> PostgreSQL RPC + telegram tables

Chat message transaction
  -> telegram_notification_outbox
    -> server-only worker endpoint
      -> Telegram Bot API
```

The browser never receives `TELEGRAM_BOT_TOKEN` or `SUPABASE_SERVICE_ROLE_KEY`. Client-side Supabase access remains protected by RLS. Webhook and worker operations use a separate server-only service-role client with sessions disabled.

## Data Model

Add migration `supabase/migrations/003_telegram_bot_relay.sql` without rewriting migrations `001` or `002`.

- `telegram_link_tokens`: stores a hash, owner profile ID, expiry, used timestamp, and creation timestamp. The raw token exists only in the generated deep link and is never persisted or logged.
- `telegram_identities`: stores the unique Telegram user ID, private chat ID, optional username, linked profile ID, status, and timestamps. This is separate from legacy `telegram_accounts` so the old fake User Bridge model cannot mutate Bot API identity data.
- `telegram_relay_log`: stores the Centras message ID, Telegram user/message IDs, direction, and timestamps. Unique constraints provide webhook idempotency.
- `telegram_notification_outbox`: stores eligible outbound events, payload, destination, status, attempts, lease, next retry time, and last safe error code.

Add security-definer RPCs restricted to service-role usage for:

- atomic link-token claim and identity linking;
- atomic inbound message insert plus relay-log insert;
- leasing outbox rows and completing/failing a delivery.

RLS remains enabled on all new tables. Authenticated users can read their own identity and relay activity. Only server-side webhook/worker code can consume tokens, mutate identities, insert inbound messages, and update outbox state.

## Flows

### Link flow

1. Authenticated user requests a link token through `TelegramService`.
2. Server/provider generates a cryptographically random short token, stores only its hash with a short expiry, and returns a deep link using `TELEGRAM_BOT_USERNAME`.
3. User opens the link and presses Start in Telegram.
4. Webhook validates `X-Telegram-Bot-Api-Secret-Token`, atomically claims the token, rejects expired/used tokens, and prevents one Telegram identity from belonging to two profiles.
5. Webhook sends a confirmation message through Bot API. A confirmation-send failure does not roll back the committed link.

### Notification flow

1. A direct message is stored normally.
2. If the recipient is `OFFLINE` or `AWAY`, has a linked identity, and `user_settings.telegram_enabled` is true, the same server-side operation creates one outbox row.
3. Worker leases pending rows and calls `sendMessage` with a short sender/content preview and a stable conversation correlation in the outbox payload.
4. HTTP 429/5xx/network errors retry with bounded exponential backoff and capped `Retry-After` support. Permanent 4xx errors become `failed` and stop retrying.
5. Successful completion atomically marks the outbox row sent and writes the outbound relay log used for inbound correlation.

### Inbound flow

1. Webhook accepts private text/caption messages from a linked Telegram identity.
2. It ignores unsupported chats/media without creating profiles or conversations.
3. An atomic RPC resolves the direct conversation from the Telegram reply-to outbound message ID, or from a single unambiguous outbound relay-log correlation, verifies membership, inserts a normal `messages` row, and writes one inbound relay log row. Uncorrelated or ambiguous messages are safely rejected rather than routed to an arbitrary coworker.
4. Existing Supabase Realtime delivers the message to the normal chat UI.

## Server Modules

- `lib/telegram/config.ts`: validates server-only Telegram environment variables.
- `lib/telegram/bot-api.ts`: typed `fetch` wrapper for `sendMessage` and webhook setup, with no UI concerns.
- `lib/telegram/repository.ts`: service-role database operations and RPC calls only.
- `lib/telegram/outbox-worker.ts`: lease, send, retry, and completion policy.
- `app/api/telegram/webhook/route.ts`: HTTP validation, Telegram update parsing, and orchestration only.
- `app/api/telegram/worker/route.ts`: secret-protected worker trigger; no browser access.
- `services/telegram-service.ts`: client-safe link/disconnect/status/activity API only.

No component imports `bot-api`, `repository`, service-role clients, or server secrets.

## Environment

Server-only:

```text
SUPABASE_SERVICE_ROLE_KEY=
TELEGRAM_BOT_TOKEN=
TELEGRAM_BOT_USERNAME=
TELEGRAM_WEBHOOK_SECRET=
TELEGRAM_WEBHOOK_URL=
TELEGRAM_WORKER_SECRET=
```

`TELEGRAM_WORKER_SECRET` must be a dedicated URL-safe value of at least 32
characters; surrounding whitespace is trimmed before it is used.

`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` remain unchanged. No Telegram secret uses the `NEXT_PUBLIC_` prefix.

## Error Handling And Security

- Missing server configuration returns `503`; invalid webhook secret returns `401`; non-POST webhook requests return `405`.
- Webhook updates are acknowledged with `200` after safely ignoring duplicates or unsupported content, preventing endless Telegram retries.
- Tokens, bot tokens, service keys, full message text, and Telegram private identifiers are not logged.
- Webhook parses only private chats and bounded text/caption payloads.
- Database uniqueness plus atomic RPCs, not a read-then-insert check, enforce idempotency.
- Worker leases prevent two workers from sending the same pending row concurrently; delivery remains at-least-once, so accepted-send/database uncertainty can produce duplicates and is not exactly-once.
