# Centras Chat — архитектура сервиса и дорожная карта UX

Дата: 2026-09-05. Статус: фазы 0, 1 и 2 (§5) реализованы — см. PROJECT.md, задачи 15–16 и `docs/GATEWAY.md`; фаза 3 (UX второй круг) и 4 — впереди.

## 1. Что есть сейчас (факты из кода)

| Слой | Как работает | Что это значит на практике |
|------|--------------|----------------------------|
| Данные | Клиент (браузер и Electron) ходит **напрямую в Supabase**: PostgREST с anon-ключом + RLS, Supabase Auth, Realtime `postgres_changes` | Бизнес-логика размазана между клиентом и RLS-политиками; любая новая интеграция = ещё один клиент БД |
| Список чатов | `getConversations` делает **4 запроса на каждый диалог** (последнее сообщение, членство, точка прочтения, счётчик) — `lib/provider/supabase-provider.ts:276-326` | 20 чатов = ~80 запросов при каждом открытии и после каждого «прочитано». На корпоративном интернете это заметные 300–800 мс |
| Сообщения | `getMessages` грузит **всю историю** без пагинации | Диалог на 5 000 сообщений тянет всё сразу; таймлайн не виртуализирован |
| Realtime | Один канал на открытый диалог; на каждый INSERT — ещё один запрос за строкой | Список чатов слева **не обновляется**, пока не переключишься; нет typing/presence |
| Серверная логика | Только Telegram-релей: `app/api/telegram/{webhook,worker,account}` — API-роуты Next.js | Нужен публичный HTTPS-хостинг Next **и** внешний планировщик, дергающий `/api/telegram/worker` раз в минуту. **Упакованный десктоп эти роуты не выполняет** (он раздаёт статику), значит релей живёт отдельно от приложения в любом случае |
| Десктоп ↔ сервер | Диалог «подключение к серверу» просит URL Supabase **и anon-ключ** | Сотруднику приходится вводить ключ базы; централизованно сменить бэкенд для всех клиентов нельзя |
| Интеграции | Нет событийной шины; Telegram — единственная и вшита в код | Каждая следующая интеграция (почта, Jira, КИАС) — снова код в приложении |

Вывод: приложение уже «серверное» — только сервер сейчас размазан по Next-роутам, RLS и cron снаружи. Идея пользователя «подключаться к серверу, а не к БД, а сервер держать отдельным лёгким процессом» — правильная, и она укладывается в один небольшой компонент.

## 2. Три варианта и выбор

| Вариант | Суть | Плюсы | Минусы | Вердикт |
|---------|------|-------|--------|---------|
| **A. Supabase-direct+** | Оставить прямой доступ, добавить SQL-функции (RPC) и Edge Functions, интеграции через Supabase Database Webhooks → n8n | Минимум эксплуатации | Edge Functions = Deno, отдельный деплой и отладка; релей Telegram переписывать; десктоп всё равно вводит ключ БД; нет единой точки для событий | Частично: RPC и пагинацию берём в любом случае |
| **B. Лёгкий шлюз (gateway) + Supabase как ядро + n8n как шина интеграций** (см. также B-full в §2.1) | Один Node-сервис (Hono/Fastify, ~60 МБ образ, 60–120 МБ RAM) рядом с Supabase | Клиенты знают **один адрес сервера**; сервер выдаёт им конфиг; вся серверная логика и планировщик внутри; события → n8n по вебхуку; Realtime и Auth остаются готовыми из Supabase | Ещё один процесс в эксплуатации (Docker или Windows-служба) | **Рекомендуется** |
| **C. Полностью свой сервер** (свой auth, свой WebSocket, Postgres напрямую) | Убрать Supabase | Полный контроль, on-prem без Supabase | Переписать Auth, Realtime, Storage, RLS; месяцы работы | Позже, если понадобится on-prem; шлюз из варианта B — точка, за которой это можно сделать незаметно для клиентов |

**Почему не n8n как основной сервер.** n8n — это движок интеграций: вебхуки, расписания, коннекторы. Он не держит тысячи WebSocket-соединений, не даёт задержку в десятки миллисекунд на доставку сообщения и выполняет workflow последовательно в очереди. Его место — **шина событий и интеграций** (паттерны «Webhook Processing», «Scheduled Tasks», «HTTP API Integration»), а не путь доставки сообщений между сотрудниками.

## 2.1 «А если n8n подключить к базе как шину, чтобы ключей БД у меня не было?»

Здесь два разных вопроса, и у них разные ответы.

### Ключи БД в клиенте — их можно не держать вообще

| Уровень | Что знает клиент (веб и установщик) | Кто держит ключи |
|---------|--------------------------------------|------------------|
| Сейчас | URL Supabase + anon-ключ (вводится в диалоге подключения или вшивается в сборку) | клиент |
| Вариант B (шлюз выдаёт конфиг) | только адрес сервера; anon-ключ приходит по `/bootstrap` в рантайме | клиент получает публичный ключ, но не хранит его в установщике |
| **Вариант B-full (рекомендуется при требовании «без ключей»)** | **только адрес сервера и свой логин/пароль** | **шлюз** — единственный, у кого есть `service_role` и URL Supabase |

В B-full клиент никогда не обращается к базе: вход, список чатов, сообщения, файлы и realtime идут через шлюз (REST + один WebSocket/SSE-канал на клиента). Шлюз подписывается на Postgres один раз (Supabase Realtime или `LISTEN/NOTIFY`) и раздаёт события клиентам сам. Цена относительно B — примерно +2–3 дня: свой WebSocket-слой, серверная проверка сессии, прокси для загрузки файлов. Взамен: клиент не знает про Supabase вообще, а значит завтра под шлюзом может оказаться обычный Postgres (вариант C) без единого изменения в клиенте.

Замечание по существу: anon-ключ Supabase — публичный по дизайну (он ничего не разрешает без JWT пользователя и RLS), и его утечка не равна утечке пароля от базы. Но требование «ключей в клиенте нет» само по себе разумное — оно убирает вопрос из аудита и упрощает смену бэкенда. B-full его выполняет.

### n8n «по базе данных» — да, но со стороны сервера, не клиента

n8n действительно умеет сидеть на базе напрямую: узел **Postgres Trigger** слушает `LISTEN/NOTIFY` (триггер `AFTER INSERT ON messages` → `pg_notify('centras_events', json)`), а Supabase даёт **Database Webhooks** (pg_net) — обе схемы отдают событие в n8n без участия шлюза и клиента. Ключи БД при этом лежат в n8n (серверная сторона, credentials в его хранилище) — это нормально. Так что как **шина событий** «n8n ↔ база» подходит и даже проще outbox-а в шлюзе; минус — нет ретраев и dead-letter (если n8n лежал, NOTIFY потерян; Database Webhooks дают ограниченные повторы). Компромисс: триггер пишет в таблицу `integration_outbox`, n8n забирает её по расписанию каждые 10–30 с — надёжно и без шлюза.

### n8n как API для клиентов (клиент → вебхуки n8n → база) — не рекомендуется

Это единственный способ обойтись без шлюза **и** без ключей в клиенте, поэтому стоит объяснить, почему он проигрывает:

| Критерий | n8n как API | Шлюз (B-full) |
|----------|-------------|---------------|
| Задержка одного действия | 150–500 мс на выполнение workflow (self-hosted), больше в облаке | 5–30 мс |
| Realtime | Нет WebSocket/SSE → клиенты опрашивают каждые 3–5 с. 200 сотрудников × 15 запросов/мин ≈ **3,5 млн выполнений в месяц** — в n8n Cloud это тариф, в self-hosted — очередь и БД выполнений | один канал на клиента, push |
| Аутентификация сотрудника | Вебхук знает только общий header-токен; кто именно пользователь — проверять в Code-узле вручную (JWT, сессии). Общий токен в установщике = один секрет на всю компанию — хуже, чем anon-ключ + личный JWT | стандартная проверка сессии в коде, RLS как вторая линия |
| Авторизация к данным | n8n ходит одной ролью в базу → все правила «кто что видит» переписываются в workflow, RLS не участвует | RLS + правила в коде |
| Приватность | n8n по умолчанию **сохраняет payload каждого выполнения** (тексты сообщений) в своей БД; нужно выключать для каждого workflow | логи без содержимого сообщений |
| Сопровождение | ~20 экранных операций = 20 workflow без типов, тестов и ревью в git | TypeScript, тесты, тот же репозиторий |

Где n8n как API уместен: редкие административные операции и интеграции (создать группу из ERP, разослать дайджест, принять заявку с формы) — то есть ровно роль шины.

### Итог для решения

- Требование «ключей БД в клиенте нет» → **шлюз в режиме полного прокси (B-full)**; клиент знает только адрес сервера.
- Требование «n8n как шина по базе» → **да**: `integration_outbox` в Postgres + n8n Postgres Trigger/расписание; ключи БД живут в n8n и шлюзе, оба на сервере.
- n8n как замена серверу для сообщений сотрудников → нет, по причинам выше.

## 2.2 Нужен ли n8n вообще?

Короткий ответ — **нет, не обязателен**. Единственная абстракция, которая действительно нужна, — таблица `integration_outbox` в Postgres (событие → надёжная доставка потребителю). Кто потребитель — деталь:

| Потребитель outbox | Что даёт | Что стоит |
|--------------------|----------|-----------|
| **Коннекторы внутри шлюза** (Telegram уже написан и покрыт тестами; e-mail через SMTP — ~1 день; универсальный «отправить событие на URL с HMAC-подписью» — ~0,5 дня) | Всё в одном репозитории: TypeScript, тесты, ревью, один процесс в эксплуатации, нет второй БД с текстами сообщений | Каждое новое правило маршрутизации — релиз приложения |
| **n8n** | Администратор меняет правила и добавляет интеграции (Jira, КИАС, почта) без релиза; готовые узлы; расписания | Ещё один сервис (300–500 МБ RAM), своя БД выполнений (нужно отключать сохранение payload), workflow живут вне git (экспорт JSON руками), при n8n Cloud — тариф по выполнениям |

Когда n8n оправдан: в компании он **уже стоит** для других процессов, планируется **три и больше** интеграций с меняющимися правилами, или логикой интеграций владеют не разработчики. Ни одно из этих условий сейчас не подтверждено.

Решение: фаза 2 переформулирована в «коннекторы в шлюзе». Универсальный webhook-коннектор с HMAC — это и есть будущая интеграция с n8n (или с чем угодно), поэтому дверь остаётся открытой бесплатно: если n8n понадобится, он просто подписывается на тот же outbox как ещё один URL. Ничего в клиенте, базе или шлюзе для этого менять не придётся.

## 3. Целевая архитектура (вариант B)

```
 Браузер / Electron ──(1) GET /bootstrap──────▶ ┌──────────────────────────┐
        │                                       │  centras-gateway (Node)  │
        │ (2) Auth + PostgREST + Realtime       │  · bootstrap / health    │
        ▼                                       │  · агрегированные чтения │
 ┌──────────────┐   (3) service-role, RPC        │  · команды с правилами   │
 │   Supabase   │◀──────────────────────────────▶│  · outbox событий        │
 │ Postgres/RLS │   (4) слушает INSERT messages  │  · Telegram webhook +    │
 │ Auth/Realtime│───────────────────────────────▶│    внутренний планировщик│
 │ Storage      │                                └─────────┬────────────────┘
 └──────────────┘                                          │ (5) HMAC-подписанные
                                                           ▼     события
                                                    ┌────────────┐  (6) команды бота
                                                    │    n8n     │─────────────────▶ gateway
                                                    │ workflows  │──▶ Telegram / почта /
                                                    └────────────┘    Jira / КИАС ERP
```

1. Клиент вводит **только адрес сервера компании** (`https://chat.company.kz`). `GET /api/v1/bootstrap` возвращает `supabaseUrl`, `anonKey`, включённые функции, брендинг, минимальную версию клиента. Ключ БД сотрудник больше не видит и не вводит; смена бэкенда — правка одного конфига на сервере.
2. Тяжёлые и чувствительные к задержке вещи остаются прямыми: вход (Supabase Auth), Realtime-подписки, загрузка файлов в Storage. Это то, что Supabase делает лучше самописного и что не стоит проксировать.
3. Шлюз держит `service_role` **только у себя** и использует его для интеграций и агрегаций; пользовательские команды выполняются с JWT пользователя (RLS остаётся последней линией защиты).
4. Один серверный слушатель `messages` (вместо N клиентских) наполняет **outbox событий**: `message.created`, `message.mentioned`, `conversation.created`, `member.added`, `file.uploaded`, `user.status_changed`.
5. Outbox доставляется в n8n вебхуком: заголовки `X-Centras-Signature` (HMAC-SHA256 от тела с общим секретом), `X-Centras-Event-Id` (идемпотентность), ретраи с экспоненциальной задержкой, dead-letter в таблицу `integration_outbox` — та же модель, что уже есть у Telegram-outbox, только общая.
6. Обратно n8n ходит в шлюз с bot-токеном: `POST /api/v1/integrations/messages` (написать в диалог от имени системного бота), `POST /api/v1/integrations/conversations` (создать группу), `GET /api/v1/integrations/users` (справочник).

### 3.1 API шлюза (минимальный набор)

```
GET  /healthz, /readyz, /version
GET  /api/v1/bootstrap                         → конфиг клиента (публичный)
GET  /api/v1/conversations                     → один SQL: последнее сообщение, непрочитанные, участники   [JWT]
GET  /api/v1/conversations/:id/messages?before=&limit=50                                                   [JWT]
POST /api/v1/conversations/:id/read            → last_read_message_id                                      [JWT]
POST /api/v1/messages                          → отправка с правилами (упоминания, лимиты вложений)        [JWT]
POST /api/v1/integrations/messages             → сообщение от бота                                         [bot token]
POST /api/v1/integrations/conversations        → создать группу / добавить участников                      [bot token]
POST /api/v1/telegram/webhook                  → перенос из Next API route (тот же код lib/telegram/*)
```
Планировщик Telegram-outbox и доставка событий — внутренние таймеры шлюза; внешний cron больше не нужен.

### 3.2 Схема события (для n8n)

```json
{
  "id": "evt_01J…",
  "type": "message.created",
  "occurred_at": "2026-09-05T15:00:12Z",
  "conversation": { "id": "…", "name": "Проект КИАС", "type": "GROUP" },
  "actor": { "id": "…", "name": "Алия Сериковна", "email": "…" },
  "message": { "id": "…", "text": "…", "mentions": ["…"], "attachments": [{ "name": "…", "size": 24576, "url": "…" }] }
}
```
В n8n данные вебхука лежат в `$json.body` (частая ошибка — обращаться к `$json.type` напрямую).

### 3.3 Workflow в n8n (по паттернам)

| # | Паттерн | Workflow | Узлы |
|---|---------|----------|------|
| 1 | Webhook Processing | **Маршрутизатор уведомлений**: событие → проверить подпись → взять настройки получателя (`user_settings`) → Switch по каналу → Telegram / e-mail / ничего | Webhook → Code (HMAC) → HTTP Request (gateway `/users/:id/settings`) → Switch → Telegram / Send Email → Respond 200 |
| 2 | Scheduled Tasks | **Утренний дайджест** 09:00: непрочитанное за ночь по группам → сообщение бота в личку каждому | Schedule → HTTP Request (gateway digest) → Split In Batches → HTTP Request (`/integrations/messages`) |
| 3 | HTTP API Integration | **КИАС → чат**: событие ERP (заявка, согласование) → сообщение в рабочую группу отдела | Webhook/Schedule → HTTP Request (КИАС) → Set → HTTP Request (`/integrations/messages`) |
| 4 | Error Handler | Любая ошибка workflow → сообщение в группу «ИТ-поддержка» | Error Trigger → HTTP Request (`/integrations/messages`) |

Telegram-релей при этом можно **оставить в шлюзе** (он уже написан и покрыт тестами) или со временем перенести в workflow №1 — второй вариант даёт администратору менять правила без релиза приложения.

### 3.4 Эксплуатация

- `docker-compose.yml`: `gateway` (node:20-alpine, ~60 МБ, 60–120 МБ RAM), `n8n` (300–500 МБ RAM, том для данных), при необходимости `caddy` для TLS. Supabase — облако или self-hosted (self-hosted Supabase — 8+ контейнеров, это уже не «лёгкий сервер», поэтому по умолчанию облако).
- Без Docker (Windows-сервер в офисе): шлюз как служба через NSSM, n8n аналогично; TLS через IIS/ARR или Caddy.
- Секреты только на сервере: `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, `N8N_WEBHOOK_SECRET`, `INTEGRATION_BOT_TOKEN`. Существующий zero-trust сканер сборки установщика продолжает гарантировать, что они не попадут в клиент.

## 4. UX / UI / отзывчивость — что улучшать и почему

Разбито на «воспринимаемую скорость», «живость», «ясность» и «управление». Каждая строка — самостоятельная задача.

### 4.1 Воспринимаемая скорость
- **Оптимистичная отправка**: сообщение появляется сразу со статусом «отправляется» (часики), затем галочка; при ошибке — «не отправлено, повторить». Сейчас UI ждёт ответ сервера.
- **Скелетоны** вместо пустоты при загрузке списка и таймлайна; кэш последнего списка чатов в памяти — переключение между разделами мгновенное.
- **Пагинация сообщений** по 50 с подгрузкой при прокрутке вверх («Загрузить более ранние») и виртуализация длинных таймлайнов.
- **Один запрос на список чатов** (RPC `conversations_overview(user_id)` или эндпоинт шлюза) вместо 4×N.

### 4.2 Живость
- **Realtime для списка чатов**: новое сообщение в любом диалоге двигает его вверх и увеличивает счётчик без переключения (подписка на `conversation_members` пользователя или SSE от шлюза).
- **Печатает…** и **присутствие** через Supabase Realtime Presence (канал на диалог): статусы «в сети» станут настоящими, ручные останутся для «Не беспокоить/Отошёл».
- **Прочитано**: под своим последним сообщением — «Прочитали: Алия, Данияр» (данные `last_read_message_id` уже приходят вместе с участниками).
- **Индикатор соединения** в titlebar вместо статичной плашки «Защищённое соединение»: «Подключено / Переподключение… / Нет сети», композер в офлайне ставит сообщения в очередь.

### 4.3 Ясность
- Убрать **нефункциональные** кнопки звонков (сейчас `alert('Аудиосвязь WebRTC подключена')`) или пометить «Скоро»; ничего не должно обещать того, что не работает.
- **Тосты** вместо `alert()` для ошибок и подтверждений; единый компонент.
- **Превью вложений**: картинки миниатюрой прямо в ленте, drag-and-drop и вставка из буфера в композер, прогресс загрузки.
- **Ссылки** кликабельны (linkify), длинные сообщения — «Показать полностью».

### 4.4 Управление
- **Командная палитра** по Ctrl+K: чаты, контакты, действия («Создать группу», «Настройки»), а не только фильтр списка.
- **@упоминания** с автодополнением из участников; событие `message.mentioned` для интеграций.
- **Alt+↑ / Alt+↓** — предыдущий/следующий чат; **«Без звука» на диалог** (mute) и «Закрепить» — нужна таблица `conversation_preferences`.
- **Тёмная тема** — токены уже в `globals.css`, нужен второй набор значений и переключатель.
- **Мобильная ширина веб-версии**: до 1024 px список чатов — выдвижная панель, панель «О группе» уже оверлей.

## 6. Что нужно решить до старта

1. **Где живёт сервер**: Docker на Linux-VM (рекомендуется), Windows-сервер через NSSM, или пока Supabase Cloud без шлюза (тогда только фаза 0 и Database Webhooks → n8n).
2. **Интеграции**: какие каналы уведомлений нужны кроме Telegram (e-mail? КИАС?). n8n — только если он уже используется в компании (§2.2).
3. **Единый адрес сервера для сотрудников** — какой домен, есть ли TLS-сертификат (для Telegram webhook он обязателен).
4. **Звонки**: убрать кнопки до реализации или оставить с пометкой «Скоро» (реальный WebRTC — отдельный проект с TURN-сервером).
5. **Тёмная тема** — нужна ли в первом релизе.

## 7. Риски и как их закрыть

- **Расхождение RLS и логики шлюза** — пользовательские операции идут с JWT пользователя, RLS проверяет всё повторно; service-role только для бота и агрегаций.
- **Дубли событий в n8n** — `X-Centras-Event-Id` + таблица доставленных в n8n (или Code-узел с дедупом по id в static data).
- **Потеря событий при падении n8n** — outbox с ретраями и dead-letter; статус доставки виден в админке (таблица «Интеграции»).
- **Версионирование клиентов** — `bootstrap.minClientVersion`; старый десктоп показывает «Обновите приложение» вместо тихих ошибок.
- **Секреты в клиенте** — сохраняется существующий zero-trust сканер сборки; anon-ключ по-прежнему публичный по дизайну Supabase.

## 8. Как сделать так, чтобы всё работало «чётко»

Надёжность здесь — не свойство одной технологии, а дисциплина из четырёх частей: решения зафиксированы, контракт один, проверки автоматические, у каждой фазы есть критерий «готово».

### 8.1 Решения по умолчанию (если не сказано иное)

| Вопрос | Решение | Почему |
|--------|---------|--------|
| Режим шлюза | **B-full** — клиент знает только адрес сервера | Требование «ключей БД в клиенте нет» |
| Ядро данных | Supabase Cloud (Postgres, Auth, Storage) за шлюзом | Уже написано и проверено; смена ядра позже не затрагивает клиентов |
| Шина событий | Таблица `integration_outbox` в Postgres; n8n забирает по расписанию (10–30 с) и/или Postgres Trigger | Переживает простой n8n, есть повторы и dead-letter |
| Хостинг | `docker-compose`: `gateway` + `n8n` + `caddy` (TLS) на Linux-VM; запасной вариант — Windows-служба через NSSM | Один файл, одна команда `docker compose up -d` |
| Доступ к данным в клиенте | Через существующий `IDataProvider`: новый `GatewayDataProvider`, mock-провайдер остаётся для демо | UI не меняется, режим выбирается конфигом |
| Идентификация клиента | Supabase Auth через шлюз (пароль → сессия), токен хранится в DPAPI-хранилище на десктопе и в `httpOnly` cookie в вебе | Ключей БД в клиенте нет вовсе |

### 8.2 Один контракт вместо договорённостей «на словах»

- **OpenAPI** для шлюза (`server/openapi.yaml`) — из неё генерируется типизированный клиент (`lib/api/gateway-client.ts`), который используют и веб, и десктоп. Ручных `fetch` в компонентах нет.
- **Схема событий** версионируется полем `v` (`message.created` v1); n8n-workflow проверяют версию и подпись первым узлом.
- **Валидация на входе** (zod) для каждого запроса и каждого события — мусор отбрасывается на границе, а не падает внутри.
- **Идемпотентность**: клиент генерирует `client_message_id` (UUID) для каждого сообщения; повтор при обрыве сети не создаёт дубль. У событий — `event_id`; у вызовов бота — заголовок `Idempotency-Key`.
- **Миграции только через `supabase/migrations`** с номером и проверкой в CI; ручных правок схемы в проде нет.

### 8.3 Автоматические проверки — что запускается и когда

| Проверка | Инструмент | Когда |
|----------|-----------|-------|
| Типы | `tsc` для приложения, `electron/`, `server/` | каждый коммит |
| Юнит-тесты | Vitest (сейчас 199) + тесты шлюза (маршруты, outbox, подпись HMAC, идемпотентность) | каждый коммит |
| Контрактные тесты | supertest против шлюза с тестовой БД (pg-mem или тестовый проект Supabase) — каждый эндпоинт из OpenAPI | каждый коммит |
| E2E-смоук | Electron-скрипт (уже используется для снимков): вход → отправить → получить во втором окне → «прочитано» → перезапуск и восстановление сессии | каждый PR |
| Сборка установщика | `electron-builder --dir` + запуск exe + снимок окна (уже автоматизировано) | каждый PR; полный NSIS — на тег |
| Безопасность | zero-trust сканер сборки (есть), `npm audit --omit=dev`, проверка, что `service_role` не попал в клиентские бандлы (`grep` по `.next/static`) | каждый PR |
| Lint | ESLint-конфиг (сейчас отсутствует — известная проблема в PROJECT.md) | каждый коммит |
| Команда «одной кнопкой» | `npm run verify` = typecheck + test + build; CI (GitHub Actions) гоняет её и выкладывает установщик как артефакт | всегда |

Правило: красная проверка — фаза не считается завершённой, коммит в `main` не делается.

### 8.4 Критерии «готово» для каждой фазы

| Фаза | Готово, когда |
|------|---------------|
| 0 | Список чатов — 1 запрос (RPC) вместо 4×N, p95 < 300 мс на 50 чатах; история постранично по 50; новое сообщение в другом диалоге двигает его вверх без переключения; «печатает…» и присутствие видны в двух окнах; при обрыве сети баннер и очередь отправки; кнопок-заглушек нет; e2e-смоук зелёный |
| 1 | `docker compose up -d` поднимает шлюз и n8n; `/healthz` и `/readyz` 200; десктоп и веб подключаются **по одному адресу**, в конфиге и установщике нет URL/ключей Supabase; Telegram-релей работает через шлюз без внешнего cron (существующие тесты релея проходят); событие `message.created` доставлено в тестовый вебхук n8n с валидной подписью, повтор при 500 сработал, dead-letter виден в админке |
| 2 | 4 workflow импортированы из `docs/n8n/*.json`, у каждого первый узел — проверка подписи/версии, «Save execution data» выключен для чатовых событий; ошибка workflow приходит сообщением в группу ИТ; дайджест приходит в назначенное время |
| 3 | Командная палитра, упоминания, превью вложений, «прочитано», mute, тёмная тема — каждая фича с e2e-сценарием и снимком в `docs/design/` |
| Каждая | PROJECT.md и документация обновлены, версия в `package.json` поднята, установщик собран и запущен |

### 8.5 Эксплуатация после запуска

- **Наблюдаемость**: структурированные логи шлюза (pino) **без текстов сообщений**; метрики — задержка запросов, длина и возраст `integration_outbox`, число WebSocket-соединений; страница «Интеграции» в админке показывает очередь и ошибки доставки.
- **Обновления клиентов**: `bootstrap.minClientVersion` — устаревший десктоп показывает «Обновите приложение» вместо тихих ошибок; в перспективе `electron-updater` с `latest.yml` (уже генерируется сборкой).
- **Секреты**: только в env шлюза и в credentials n8n; ротация — через перезапуск контейнера; в репозитории и установщике их нет по построению (сканер сборки).
- **Резерв**: ежедневный бэкап Postgres (Supabase делает сам; для self-hosted — `pg_dump` в compose-cron), экспорт workflow n8n в git.
- **Runbook** в `docs/OPERATIONS.md`: как поднять, как обновить, как откатить (тег образа), что смотреть при «сообщения не доходят» (очередь outbox → логи шлюза → статус Realtime).

### 8.6 Порядок работ, чтобы ничего не ломать по дороге

1. Фаза 0 в текущем стеке — даёт скорость и живость сразу, не требует сервера.
2. Шлюз строится **параллельно** и включается флагом провайдера: сначала на staging, потом для одного отдела, потом для всех. Откат — переключить флаг обратно.
3. Только после того как все клиенты на шлюзе, из клиента удаляется код прямого доступа к Supabase и ключи исчезают из сборки окончательно.
4. n8n подключается к `integration_outbox` последним — к этому моменту события уже пишутся и видны в админке, workflow отлаживаются на реальных данных без риска для чата.

## 9. Ответы на вопросы после просмотра веб-версии (2026-09-06)

### 9.1 «Интерфейс усложнён» — что убрано

Telegram спрятан за флагом `NEXT_PUBLIC_FEATURE_TELEGRAM` (выключен по умолчанию: нет в рейке, настройках и админке; серверный код сохранён). Из titlebar ушли плашка «Защищённое соединение» и переключатель звука — остался точка-индикатор состояния (зелёная/жёлтая/красная) и текст только при проблеме. Из шапки чата убран «колокольчик», из композера — подсказка про Enter/Shift+Enter (осталась во всплывающей подсказке кнопки). Из списка чатов убрана дублирующая ссылка «Справочник» (Контакты уже в рейке). Демо-аккаунты на входе показываются только в демо-режиме. Вкладки «Интеграции» и «Telegram-бот» в админке появляются только когда включены.

### 9.2 «База данных вообще нужна?»

Нужна — но не обязательно облачная. Без хранилища нет истории, поиска, доставки офлайн-сотрудникам и файлов «на потом»: сообщения существовали бы только пока оба онлайн. Правильная формулировка требования — **«всё на своём сервере, без облака»**. Это достижимо: PostgreSQL в контейнере рядом со шлюзом (или self-hosted Supabase, если хочется сохранить Auth/Realtime/Storage как есть). Шлюз — та граница, за которой ядро меняется незаметно для клиентов (фаза 4 дорожной карты).

### 9.3 «По localhost можно поставить всё соединение?»

«Localhost» буквально — только один компьютер. Для команды нужен один **сервер в локальной сети** (офисная машина или ВМ): на нём `docker compose up -d` (шлюз + Postgres + Caddy), у сотрудников в приложении — адрес `https://chat.local` или `http://192.168.x.x:8080`. Интернет не нужен вообще. TLS внутри сети: либо Caddy с внутренним CA (сертификат раздаётся установщиком), либо HTTP внутри доверенного VLAN — первое предпочтительнее, потому что звонки (WebRTC) и уведомления браузера требуют защищённого контекста.

### 9.4 «Передача файлов напрямую безопасна?»

Напрямую между компьютерами (WebRTC data channel) канал шифруется (DTLS), но: файл недоступен, если отправитель офлайн; нет истории и повторной загрузки; нет антивирусной проверки и аудита; в сети с изоляцией портов P2P часто не проходит. Для корпоративного чата надёжнее **через сервер**: загрузка в хранилище шлюза (локальный диск или MinIO), доступ только участникам диалога, лимит размера, опциональная проверка антивирусом, TLS в пути и шифрование на диске. P2P оставить для гигантских файлов как ускорение — не как основной путь.

### 9.5 «Плагины, чтобы админы подключались как через TeamViewer»

Это два разных уровня:

| Уровень | Что это | Сложность / риск | Решение |
|---------|---------|------------------|---------|
| Показ экрана в звонке (view-only) | Сотрудник делится экраном, админ видит и подсказывает | Низкая — часть WebRTC-звонков, `desktopCapturer` в Electron, явное согласие | Делаем вместе со звонками |
| Удалённое управление (мышь/клавиатура) | Полноценный TeamViewer | Высокая: нативные модули ввода, права, MFA, аудит, юридические требования | Не строим сами. Интегрируем self-hosted **RustDesk** (открытый аналог TeamViewer со своим сервером): кнопка «Запросить удалённую помощь» в чате открывает сессию с согласия сотрудника, событие фиксируется в аудите |
| «Плагины/расширения» внутри клиента | Сторонний код в приложении | Высокая: песочница, обновления, безопасность | Не сейчас. Расширяемость — через события `integration_outbox` и API бота |

### 9.6 «Звонки: аудио и видео»

Реализуемо и запланировано как основная часть фазы 3. Архитектура: **self-hosted LiveKit** (открытый SFU в Docker — аудио, видео, показ экрана, групповые звонки, встроенный TURN); шлюз выдаёт токен доступа к «комнате» диалога по JWT сотрудника; в клиенте — кнопки звонка в шапке чата (появятся, когда сервер медиа настроен, а не раньше), входящий вызов с приёмом/отклонением, панель звонка (микрофон, камера, экран, участники), запись — по решению. Сигнализация («звонит», «принял», «завершил») идёт событиями через Realtime/шлюз, чтобы работали и уведомления, и история звонков в диалоге. Оценка: 1:1 и групповой звонок с показом экрана — 6–8 дней, включая тесты и сборку установщика с разрешениями микрофона/камеры.

### 9.7 Итоговая on-prem конфигурация (без облака и без интернета)

```
Сервер в локальной сети (Docker):
  caddy (TLS, внутренний CA) ─▶ gateway ─▶ postgres (данные) · minio (файлы) · livekit (звонки) · rustdesk-server (удалённая помощь)
Сотрудники: установщик Centras Chat с адресом сервера, сертификат CA ставится установщиком.
```
Порядок работ: фаза 3a — звонки (LiveKit) и файлы через сервер; фаза 3b — RustDesk-кнопка и аудит; фаза 4 — замена Supabase на локальный Postgres за шлюзом.
